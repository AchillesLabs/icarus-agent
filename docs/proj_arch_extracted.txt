1. Executive summary and decisions
Build an open-source, CLI-first AI agent that users can run locally or deploy on their own VPS. The same agent-core powers a Typer CLI and a FastAPI service for remote execution, persistent scheduling and managed hosting. Add OAuth integrations and opt-in MCP support through permission-controlled tool adapters. A cross-platform desktop client (Tauri 2 + React/TypeScript, with the Python runtime packaged as a sidecar) is a planned later release; a browser chat UI remains out of current scope. We will operate a managed instance on AWS while users can self-host without depending on our servers.
ARCHITECTURE IN ONE SENTENCE
A modular Python monorepo managed by uv, with a shared agent-core package, a Typer CLI, a FastAPI service, and a separate worker/scheduler; SQLite for single-user local mode and PostgreSQL for server mode.

Success criteria for the first public CLI release

2. Product scope and deployment modes
The product has three supported modes. They reuse the same core business logic, but they do not share the same trust boundary or storage configuration.
2.1 Local CLI mode
The user runs the agent on their own computer with `openagent chat` or `openagent run`.
Local sessions and settings are stored under the user profile; SQLite is sufficient for an initial single-user installation.
Provider keys should be stored in the operating-system credential store when available. Local inference may be configured through a local model server.
Reminders that must trigger when no terminal is open require an always-running local daemon/service or a scheduler supplied by the operating system. A CLI process that has exited cannot deliver a notification by itself.
No platform account is required for local mode unless the user chooses to connect to a remote service.
2.2 Self-hosted VPS mode
The user deploys their own FastAPI service and worker, normally with Docker Compose.
The service owns the persistent database and runs scheduled jobs independently of the user laptop.
The user connects from any CLI installation with a named server profile and a credential: `openagent server add home --url https://agent.example.com`.
The self-hosting owner controls the VM, backups, TLS, model credentials and notification integrations.
For the standard multi-process setup, use PostgreSQL. A one-process SQLite mode can be supported as a deliberately limited option, not as the default concurrent server database.
2.3 Our managed AWS-hosted mode
The same API and worker code run on infrastructure operated by us.
Multiple unrelated users share compute and database infrastructure but have logically isolated accounts, data, credentials, runs, reminders and tool permissions.
The CLI authenticates to our endpoint and sends requests over HTTPS. Every request is scoped to the authenticated identity on the server, not to a caller-supplied user ID.
BYOK reduces our inference spend, but a remote run requires the service to use the user key. The key must be encrypted at rest and accessed only for that authorized run. A user who does not want the key to leave their device should use local execution.
Hosting is not free simply because model inference is BYOK: compute, database, storage, egress, observability and backups still incur operating cost.
2.4 Not in current scope
No browser-based chat website, mobile application, public plugin marketplace, autonomous multi-agent swarm, arbitrary code execution in shared hosting, Kubernetes rollout, or self-hosted LLM GPU serving is required for the initial CLI/server release. A cross-platform desktop app is approved as a later roadmap phase after the runtime and API contracts stabilize. It will reuse the same Python agent-core rather than implement a second agent.
3. Target architecture
The architecture is a modular monolith first: the CLI, API, worker and agent core have clean module boundaries, but we do not split every component into a network service before there is a measured need. uv workspaces allow interconnected packages to share one lockfile while remaining separately testable [1].

3.2 Core runtime contract
A run should be represented by a typed state object and a lifecycle, not a free-form infinite loop. At minimum, run state carries a run ID, owner/tenant context (server mode), session ID, task request, selected provider/model, messages/context references, tool results, approval state, cancellation signal, budget counters and final status.
Run lifecycle: queued -> running -> waiting_for_approval -> running -> succeeded
                                               |                     |
                                               |                     +-> failed
                                               +-> cancelled / expired
 
Per-run hard limits: max model turns, max tool calls, wall-clock deadline,
context/input budget, output-token budget, provider retry budget, optional spend cap.

LangGraph is recommended for graph state, checkpoints and interruptible workflows. Keep our own application policies around it: allowed tools, ownership checks, cost/time limits, idempotency, error normalization and API semantics. LangGraph describes checkpointers for thread-level state and stores for longer-term information across threads [7].

6. End-to-end workflows
6.1 Local CLI chat
1. User installs the package and runs `openagent init`. The CLI creates the application data directory, local database and config profile.
2. User configures a provider/model. The API key is saved in the OS keyring where supported; only a provider reference is written to ordinary config.
3. `openagent chat` loads the local session and calls the shared agent-core directly (no HTTP round-trip required).
4. Agent-core assembles context, checks token and run budgets, invokes the selected model adapter, and validates any returned tool calls.
5. Tool executor enforces a policy and schema before running a tool. Results are persisted and inserted into context within budget.
6. The runtime finishes, saves the run/session, emits usage metadata and returns a final answer. Exit codes distinguish success, provider failure, cancellation and configuration errors.
6.2 Self-host on a user's VPS and connect with CLI
1. User provisions a Linux VPS and installs Docker Engine/Compose, or follows a supported native installation path.
2. User creates a deployment config, a strong initial admin credential, provider configuration and a persistent data volume. Secrets are permission-restricted.
3. Compose starts the reverse proxy, FastAPI, worker/scheduler and PostgreSQL. Only HTTPS is public; database and internal service ports remain private.
4. The owner points DNS at the VPS and configures TLS. The deployment validates migration state and health before accepting client traffic.
5. On a laptop, the user runs `openagent server add home --url https://agent.example.com`, then authenticates and selects the `home` profile.
6. CLI requests use HTTPS and the configured token. FastAPI resolves the authenticated identity, authorizes the resource, persists work and streams run events back to the CLI.
7. Background tasks continue even if the laptop CLI exits. The owner monitors health, performs backups and applies upgrades.

6.3 Our managed AWS-hosted CLI service
1. User obtains an account/CLI credential through the supported enrollment flow. Access tokens are short-lived; refresh/session credentials can be revoked.
2. CLI posts a run request with an idempotency key and session reference to the HTTPS API.
3. API derives user_id/tenant_id from authenticated server-side identity, applies rate limits and quota rules, checks request schemas, and persists a run record.
4. Agent execution runs in the managed worker/runtime with the caller’s approved provider credentials and tool grants. In hosted mode, arbitrary shell/code execution is disabled by default.
5. Events are persisted or streamed using SSE. If the connection drops, the CLI can query run status and resume streaming without creating a second run.
6. Usage, outcome, provider/model, token counts and redacted audit metadata are recorded. Data-access and deletion policies are documented for users.
6.4 Agent tool-call workflow
User request
  -> Build bounded context (instructions + relevant history + allowed tools)
  -> Call model
  -> If final response: persist result and finish
  -> If tool call: validate schema and authorize tool/arguments
  -> If sensitive write: pause for approval unless an explicit policy grants it
  -> Execute with timeout/resource limits; normalize tool result/error
  -> Record result; compact context if needed; repeat within budgets
  -> Persist final status and usage

External web pages, documents, emails and plugin outputs are untrusted input. Never interpret them as policy overrides. Tool permissions are enforced in code, not granted by the model.
6.5 Reminder and scheduled-task workflow

Figure 2. Reminders are durable jobs, not prompt text the model must remember.
1. Parse the requested local time and timezone explicitly. Resolve it to an absolute UTC timestamp while retaining the original timezone for display and daylight-saving interpretation.
2. Write a durable job record: owner_id, task payload, due_at, timezone, status, delivery target, retry policy, idempotency key and schema version.
3. A scheduler finds due jobs. In PostgreSQL, workers can atomically claim rows in a short transaction (for example using row locks and `SKIP LOCKED`); do not hold a database transaction open while an LLM or external notification call runs.
4. The worker revalidates the job owner and active permission grants, then executes the reminder/agent workflow. A simple reminder should not require an LLM.
5. Deliver through a configured channel such as email or webhook. Printing in a terminal is insufficient if the terminal is closed; document what notification channels are configured.
6. Record success/failure, retry only safe failures with bounded exponential backoff and jitter, and prevent duplicate sends with idempotency or provider-supported delivery IDs.
For a small self-hosted deployment, a PostgreSQL-backed job table plus worker is a reasonable baseline. At higher AWS scale, use EventBridge Scheduler and SQS for time-triggered dispatch/retries, with a worker consuming the queue [5].
6.6 BYOK workflow
Local mode:
CLI -> OS keyring -> provider adapter -> provider API
 
Hosted/self-hosted remote mode:
CLI --HTTPS--> API -> credential reference -> decrypt only when needed -> provider adapter
 
Rules:
- Never send API keys in prompts, tool descriptions or logs.
- Never expose provider keys to the browser or other tenants.
- Encrypt server-side secrets at rest with encryption keys stored separately.
- Never silently switch to a user's paid key after a free provider quota ends.
- Tell users that remote execution means their key is processed by the server they selected.

7. Data model and user isolation
Local mode is single-user by default. Server mode is multi-user and must enforce isolation at every layer. PostgreSQL row-level security (RLS) can provide defense in depth, but policies must be correctly configured; database owners/superusers can bypass ordinary RLS behavior unless roles and policies are designed carefully [6].

7.1 Isolation invariants
Identify the current owner from a validated session/token; never trust user_id or tenant_id provided in a request body.
Every read, update and delete is scoped by both resource ID and authenticated owner. A random UUID is not authorization.
Every background job stores owner_id and rechecks ownership/permission at execution time. Queue messages are hints/identifiers, not proof of authorization.
Every memory/vector query is filtered to the owner before retrieved text enters the prompt. Test cross-tenant retrieval explicitly.
Use a restricted application DB role and consider RLS as a second guard. Add tests for policy bypass, transaction-local tenant context and connection-pool reuse.
Use tenant-scoped quotas and rate limits to prevent one user from starving other users.
7.2 Data lifecycle
Define retention and deletion behaviors before public launch. Deleting an account should revoke connected tokens, cancel queued jobs, delete or anonymize conversations/memories according to the documented policy, and remove stored credentials. Backups expire under a published retention schedule; deletion from backups may be delayed until backup rotation completes, and this must be disclosed.

8.1 API behavior standards
Use a `/v1` prefix and version contracts deliberately; breaking changes require a new version or migration policy.
Return a stable error body with a machine-readable code, safe message and correlation ID. Never return stack traces or upstream secret-bearing payloads.
Support request timeouts, client disconnect/cancellation, rate limits, payload size limits and explicit run budgets.
Use SSE for incremental run events rather than inventing a custom websocket protocol unless two-way streaming is needed.
Generate and test the OpenAPI schema in CI. The CLI remote client should consume shared typed contracts or a generated client, not hand-copy request schemas.
9. Security, reliability and token controls
9.1 Authentication and authorization
Mode
Minimum control
Local CLI
No account requirement. Use filesystem permissions and OS account boundaries; local mode warns when exposed services are enabled.
Private self-host
Bootstrap a strong initial admin credential; issue revocable client tokens; bind internal ports privately and require HTTPS for remote clients.
Managed multi-user
Authenticated account identity, short-lived access tokens, refresh/session revocation, server-derived owner context, per-user quotas and audit events. Prefer a standard OAuth/OIDC/device-login design for CLI rather than inventing an auth protocol.
Admin/operator
Separate operator/admin privileges from end-user tools. Operational access must not implicitly grant routine application access to user secrets.

9.2 Tool security
Filesystem tools are limited to approved roots; resolve paths and reject path traversal and symlink escapes.
Shell execution is disabled by default in hosted mode. If added later, use an isolated per-run container/VM with CPU, memory, process, time, filesystem and network limits.
Destructive writes, sending messages and sensitive external actions require explicit approval or a user-defined, narrowly scoped policy.
Plugins are untrusted by default. A manifest describes tools, schemas and permissions; installing a plugin does not automatically authorize all of its requested permissions.
External content is prompt-injection-prone. Keep it separate from system policy, and do not allow content to change permissions or credentials.
9.3 Context/token/cost budget
input_budget = model_context_window - output_reserve - safety_margin
 
Context order (initial policy):
1. Non-negotiable system/safety instructions
2. Current task and constraints
3. Only the tools allowed for this run
4. Retrieved owner-scoped memory/documents
5. Recent conversation messages
6. Summary of older history
 
Track: estimated input tokens, provider-reported usage, output tokens, model calls,
tool calls, elapsed time, retries and estimated cost per run.

Use model-specific token counting when possible; provider usage metadata is authoritative when provided. Never assume a single tokenizer fits every model.
Compact history before the context limit is reached. Preserve task goals, explicit constraints, pending approvals, tool outcomes and unresolved actions.
Cap tool calls, graph iterations, output tokens, provider attempts, wall-clock duration and optional spend per run.
Fallback only to a model that supports the needed tool/structured-output capabilities and fits the context budget. Respect retry-after and use bounded exponential backoff with jitter.
No silent BYOK fallback: if the user's free quota ends, ask or follow an explicit user-selected policy before using a key that may incur a charge.
9.4 Reliability and idempotency
Give each run/task a stable ID and each write/action an idempotency key when duplicate execution can cause harm.
Persist state transitions before acknowledging durable task creation. A successful HTTP response must not claim a reminder was stored unless it is committed.
Use bounded retries for transient errors only. Do not retry invalid credentials, malformed arguments or non-idempotent side effects blindly.
Worker leases must expire and be reclaimable after crashes. Record attempt count, last error category and next retry time.
Use structured JSON logs and correlation IDs; redact provider keys, OAuth tokens, sensitive prompt payloads and private file content.

10.4 Release/deploy pipeline
1. Pull request: Ruff, static type checks, unit/integration tests, security scanning, secret scanning and package build.
2. Merge to main: build an immutable container image, tag it with a commit SHA and publish it to a registry such as Amazon ECR when using AWS.
3. Deploy to staging, run database migrations as a single controlled step, wait for readiness health checks and run a smoke test through the CLI.
4. Promote the same image to production, monitor 5xx/latency/worker backlog and preserve a rollback plan. Do not run migrations concurrently in every API worker.
5. Use short-lived CI-to-AWS credentials through an identity federation/OIDC role where possible rather than long-lived access keys in GitHub secrets.
10.5 Cost boundaries
The software can be open source and users can bring their own model keys. That does not remove VPS, storage, networking, domain, email/SMS, monitoring or backup costs. Publish a clear local/self-host/managed comparison. The managed service should have hard task/request limits and per-tenant controls so a runaway agent cannot create unbounded infrastructure or provider costs.

Decision / mitigation
Provider quotas change or free models disappear
Represent provider/model availability as configurable capability data; handle 429/timeouts; BYOK remains opt-in and no paid fallback is silent.
Shared-host tool execution is unsafe

15. Integrations, OAuth and MCP
OpenAgent should offer two complementary integration paths: first-party OAuth connectors for high-value services where we need a predictable security and permission model, and an MCP client for compatible third-party tools. MCP is an interoperability layer, not a trust or safety guarantee.
15.1 First-party OAuth connectors
The user starts the connection from the CLI (the flow opens the system browser when needed) or the future desktop UI. The provider displays its consent screen. The app requests only the scopes needed for the chosen features, validates OAuth state/PKCE where applicable, stores tokens in the appropriate local or server-side secret store, and exposes only authorized operations to the tool runtime. Never ask for provider passwords.
In local CLI/desktop mode, prefer an OS credential store and an installed-app/local callback flow supported by the provider. In remote self-hosted/managed mode, use a registered HTTPS callback, bind the grant to the currently authenticated OpenAgent account, encrypt refresh tokens at rest, and allow revocation. Provider tokens and client secrets must never be included in prompts or ordinary logs. Public Google OAuth use may require verification; Gmail scopes are classified by sensitivity, and restricted-scope handling can trigger additional review requirements [13].

15.2 MCP server compatibility and trust model
Implement an MCP client adapter in agent-core. Support local stdio servers for local CLI/desktop use and authenticated remote HTTP MCP servers when their authorization and transport are compatible with the client implementation. Each server configuration must record transport, endpoint or command, version/pinning information where available, authentication reference, enabled tool allowlist and permission policy. MCP authorization guidance recommends OAuth-based authorization for remote servers that expose user-specific data or sensitive actions [12].
Do not install or launch arbitrary community MCP servers automatically. The modelcontextprotocol/servers repository describes its implementations as reference examples, not a blanket production-safe catalog [11]. Start with a small curated set and a user-added-server flow. Discovery means “available for review,” not “trusted to execute.” Bound process permissions, environment variables, timeouts, output sizes and concurrency; treat all tool descriptions and tool results as untrusted input. In a shared hosted service, do not launch an arbitrary user-supplied stdio process inside the API or shared worker. Initially allow only reviewed remote servers or isolated per-user/per-run execution designed for this purpose.
15.3 Practical first-party tool count and catalog
Do not promise hundreds of hand-written built-ins in the first release. Target 12 stable, tested core tools for the first usable release, grow toward roughly 24 first-party tools as the runtime matures, then add integration-specific actions and the long tail through MCP. Tool count is a planning target; only ship tools that have tested schemas, permissions, error handling and documentation.

16. Cross-platform desktop application
A desktop app is approved for the roadmap, while the first implementation remains CLI + FastAPI. The proposed desktop stack is Tauri 2 with React/TypeScript for the UI and the shared Python runtime packaged as a per-platform sidecar. Tauri documents sidecars specifically for bundling external executables such as Python applications or API servers, avoiding a separate Python installation for end users [14].
The desktop app will support two explicit modes. Local mode launches a bundled OpenAgent service that uses local persistence and the OS credential store. Remote mode connects to a user-selected self-hosted VPS or the managed service over HTTPS. Both modes call the same agent-core contract; the frontend must not implement a second agent loop.
